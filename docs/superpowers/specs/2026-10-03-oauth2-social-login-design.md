# OAuth2 self-serve login — Google / Microsoft

**Status:** design, approved 2026-10-03
**Supersedes nothing. Extends `auth-service` and `account-service`.** Builds on ADR-0000 §1/§2,
ADR-0013 §3 (self-serve signup), and the enterprise-SSO flow already implemented in
`services/auth/app/oidc.py`.

---

## 1. Scope and why this isn't the SSO flow that already exists

`auth-service` already has a full OAuth2/OIDC authorization-code + PKCE login flow, but it is
*enterprise SSO*: one organization admin configures one IdP (`OrgIdpConfig`) for their own
DNS-verified domain, and it only ever authenticates people **already** provisioned into that org
— JIT provisioning is explicitly inert (`OrgIdpConfig.jit_provisioning` docstring: "an unknown
email is refused"; provisioning happens through exactly one door, an invitation).

This spec adds a second, platform-owned flow: **"Continue with Google / Continue with Microsoft"**
as a consumer-facing self-serve login, usable from three entry points that all share one
mechanism, branching on what the directory already knows about the verified email:

- **New workspace** — nobody has an account yet; completing it creates an org + owner.
- **Join via invitation** — an invited email accepts using Google/Microsoft instead of setting a
  password.
- **Returning sign-in** — same button, email already has an account → straight to a session (with
  an org picker if the person belongs to more than one org, per ADR-0000 §1), no new row anywhere.

The data model already half-anticipated this: `ExternalIdentity.provider` is typed
`'google' | 'microsoft' | 'saml:<org_id>'`, but only the `saml:`/enterprise-OIDC half is wired up.

**Non-goals (v1).** An explicit "connect/disconnect Google" settings screen (auto-link on first
verified match covers the common case — decided below, §5). Any provider besides Google and
Microsoft. Per-org admin-configured Google/Microsoft (that's what `OrgIdpConfig` already is).

## 2. New data

### 2.1 `auth.platform_oauth_providers` (new table)

| column | notes |
|---|---|
| `provider` (PK) | `'google'` \| `'microsoft'` |
| `enabled` | bool |
| `client_id`, `client_secret_enc` | `client_secret_enc` via the existing `platform_core.pii.seal` envelope, same as `OrgIdpConfig.client_secret_enc` |
| `issuer`, `authorization_endpoint`, `token_endpoint`, `jwks_uri` | pinned once at bootstrap via the existing `HttpIdpClient.discover`, same pin-at-save-time reasoning as `OrgIdpConfig` |

**Not** under row-level security — this is platform-wide configuration with no `organization_id`,
the same category as `SigningKey`. Reusing `OrgIdpConfig` was considered and rejected: that
table's shape (`organization_id`, RLS, `allowed_domains`, `jit_provisioning`) is specifically "one
org's IdP"; a platform credential has no organization.

Client credentials themselves are **deployment secrets in env vars**
(`GOOGLE_OAUTH_CLIENT_ID`/`_SECRET`, `MICROSOFT_OAUTH_CLIENT_ID`/`_SECRET` on `Settings`), matching
how ADR-0013 §6 already treats Razorpay keys — seeded into the table by a one-time bootstrap
script, never accepted through any API.

### 2.2 `auth.external_identities`

Already modeled for this. No migration needed.

### 2.3 Account-service

No new tables. `create_organization`, `add_member`, `accept_invitation` are reused unchanged.

## 3. The flow

```
Browser → auth-service: GET /auth/oauth/{provider}/start?intent=signup|invite&invitation_token=...
  → same PKCE/state/nonce machinery as sso_start (new provider lookup instead of org/domain resolution)
  → redirect to Google/Microsoft

Google/Microsoft → auth-service: GET /auth/oauth/{provider}/callback?code=...&state=...
  → StateStore.consume, exchange_code, verify_id_token     (reused verbatim from oidc.py)
  → VerifiedIdentity{subject, email}

  if ExternalIdentity(provider, subject) exists:
      → mint session for that user_id (returning-user path; org picker if >1 active membership)

  elif intent == "invite":
      → account-service POST /internal/v1/invitations/accept-federated {token, provider, subject, email}
      → 404/410 "that invitation is not valid" (expired/revoked) — same sentence as today
      → 409 "that invitation is not valid" (email mismatch — see §6, deliberately not a distinct message)
      → on success: write ExternalIdentity, mint session

  else (intent == "signup"):
      → directory.find_by_email(email)   (existing read, directory.py)
      → found  → do NOT create a second org; fall through to the returning-user path (auto-link, §5)
      → not found → one screen: org name + slug (prefilled from the provider profile)
                     → account-service POST /internal/v1/signup-federated
                        {organization_name, slug, full_name, email, provider, subject}
      → account-service creates org (uuid4 id generated by auth-service, bound before write —
        same pattern as today's public signup) + owner membership, returns {organization_id, user_id}
      → write ExternalIdentity, mint session immediately
```

## 4. The two new account-service internal endpoints

Both live in `app/api/internal.py` — `require_service_token`, mounted outside `/api/v1`, same
posture as the four existing internal reads (`directory.py`'s `find_by_email`/`get`/
`resolve_domain` plus permission lookups). They are **not** variants of the public
`/account/signup` / `/invitations/accept` routes: those are reachable with no caller identity by
design (bypass-then-narrow, ADR-0002 path 4), and mixing "anyone with no account" with "auth-service,
already holding a verified identity" on one route means defending two trust levels in one schema.
Internally both call the **same service functions** that already exist — `services.signup`,
`services.accept_invitation` — only the entry schema differs (a verified email, no deferred
password).

- **`POST /internal/v1/signup-federated`** — same body as `SignupIn` (minus password, which never
  existed there), returns `{organization_id, user_id}` instead of today's `SignupOut` — auth-service
  needs `user_id` to write `ExternalIdentity`, which the public route never needed because it mints
  no session.
- **`POST /internal/v1/invitations/accept-federated`** — same shape as `InvitationAccept` plus
  `{provider, subject}`. Adds one new check inside `services.accept_invitation`, ahead of
  `add_member`: refuse if `email.lower() != invitation.email.lower()`. This is the one new
  authorization rule this spec introduces, and §6 explains why it's load-bearing.

**Idempotency.** No new idempotency-key column. A retry after a timeout hits the *same*
`slug_taken`/`get_user_by_email` 409s the public routes already return today. auth-service's retry
policy: re-run `directory.find_by_email` before retrying a write that may have already landed —
only retry the write if it genuinely didn't happen.

## 5. Why minting a session immediately doesn't reopen ADR-0013 §3

ADR-0013 §3 refused "returning a session on signup" because the email was *unverified at that
moment* — the reset-link exists specifically to verify it asynchronously. A Google/Microsoft ID
token (`verify_id_token`, already enforcing `email_verified: true`) proves the address
**synchronously**, before this flow ever calls account-service. The case the ADR refused — a live
token paired with an unverified address — doesn't occur here. This is a new case the ADR didn't
rule on, not a reversal of it.

**Auto-link decision (confirmed 2026-10-03):** if a verified email already has a password-based
account, "Continue with Google" auto-links `ExternalIdentity` and signs the person in immediately,
rather than requiring a prior explicit "connect Google" action from a settings page. One button
handles new signup, invite-accept, and return sign-in. This matches the trust model
enterprise SSO already uses for `ExternalIdentity` (§6) and avoids a v1 settings screen for a
no-new-risk case.

## 6. Security notes

- **Invitation email must match exactly.** Without the §4 check, holding an invitation link would
  let anyone accept it under their own Google identity — the invitation's authorization is "this
  token," but provisioning has always been keyed by `invitation.email`
  (`add_member(email=invitation.email, ...)`), and that must stay true regardless of which
  credential mechanism completes it.
- **Auto-link safety** rests entirely on `verify_id_token` already refusing unverified emails, and
  on `ExternalIdentity`'s uniqueness on `(provider, subject)` making every login *after* the first
  a lookup, not a re-match. Same model as enterprise SSO, no new risk class.
- **Session pinning.** `Session.idp` is set to `"oauth:google"` / `"oauth:microsoft"` —
  deliberately **not** `"oidc:<org_id>"`. `_federated_organization_pin` only recognizes `oidc:`/
  `saml:` prefixes, so these sessions stay **unpinned**, same as a password session. This is
  correct, not an oversight to fix: enterprise SSO pins because the IdP vouches for *one org's own
  domain*; personal Google/Microsoft vouches for *a person*, exactly what a password proves, so the
  person should be free to switch to any org they belong to. No change needed to that function —
  add a regression test asserting it (§8).
- `Session.amr` gains a new code, `"oauth"`.
- All egress to Google/Microsoft reuses `EgressGuard`/`HttpIdpClient` as-is — no new SSRF surface.

## 7. Error handling

Reuses the existing opaque, non-enumerating `Sso*Problem` shapes (provider disabled/misconfigured,
state replay/expiry, bad ID token). New cases follow the same posture: invitation email mismatch
is the same 404 "that invitation is not valid" as every other invitation failure (§4) — a distinct
message would tell an attacker their forged attempt was a real token, which is exactly the
enumeration the existing invitation/SSO error design already refuses elsewhere. Duplicate-account-
on-signup reuses today's 409 pointing at sign-in.

## 8. Testing

- Extend `tests/fake_idp.py` (already exists for enterprise SSO) to serve a fake Google/Microsoft
  discovery document, reused by every test below.
- `test_oauth_signup.py` — new org created; existing email does not get a second org (falls through
  to auto-link); slug collision 409.
- `test_oauth_invite.py` — happy path; **email-mismatch refusal is the adversarial case, written
  first**.
- `test_oauth_returning_user.py` — auto-link on first match; second login reuses the
  `ExternalIdentity` row without re-touching account-service; org picker with >1 active membership.
- One explicit test asserting an `oauth:*` session is **not** org-pinned (`_federated_organization_pin`
  returns `None`), guarding the §6 behavior against a future refactor that widens the prefix check.
- account-service: unit tests for both new internal endpoints behind `require_service_token`,
  including the 403 when called without a valid service token.

## 9. Rollout

Bootstrap script seeds `platform_oauth_providers` from env vars on deploy (disabled until both
`client_id`/`client_secret` are present, mirroring `payment/app/config.py`'s "inert without
Razorpay keys, by design" pattern). Frontend work (the "Continue with Google/Microsoft" buttons,
the one-screen org-name prompt) lands in `opsgrids-dashboard` per ADR-0013 §4 — out of scope for
this spec's backend plan but called out so the implementation plan sequences it.
