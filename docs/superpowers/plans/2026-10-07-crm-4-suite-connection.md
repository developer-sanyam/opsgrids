# Sub-project 4: CRM suite connection Implementation Plan (release outlines)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Link every OpsGrids product that holds a customer, a contact or a company to the CRM party (company = party, contact = person, rep = account membership), show the connected picture on the CRM 360 and company page, and carry consent and erasure through every connection, in seven independently deployable releases R4.1 to R4.7.

**Architecture:** Plain nullable `crm_company_id` and `crm_contact_id` UUID columns sit beside each product's display snapshot (no cross-schema foreign key) and are proved through idempotent internal routes on `customer` (C50, C51, C52, C53, C89) that re-check the `crm` entitlement. Events carry ids only and gain fields additively within `v1`, each with its committed schema and a producer-side test; the 360 reads CRM-held projections of finance and operations events (`party_documents`, `party_payments`, `party_rollup`, `party_timeline`) and failure-isolated live reads of support and delivery. Consent stays in `notification`; an erase anonymises in place and emits `crm.book.contact.erased`; every consumer deploys before its producer and every projection has an owner-run backfill; no release adds a container except the `insights` container that ADR-0020 already decided.

**Tech Stack:** Python 3.12 FastAPI services (SQLAlchemy 2, Alembic, PostgreSQL with a schema per service and forced row-level security, RabbitMQ events through the transactional outbox in `platform_core.events`), JSON Schema contracts in `libs/contracts`, uv, pytest, mypy, ruff and import-linter run per service, React 19 and TypeScript 5 SPAs in the pnpm workspace under `frontend/` (vitest, Storybook stories, the visual and axe harness), Make targets (`make check`, `make gate`, `make openapi-check`, `make migration-roundtrip`, `make ui-visual`) and the one-box edge tooling (`make deploy`, `make edge-reconcile`, `make edge-web`).

**Spec:** `docs/superpowers/specs/2026-10-07-crm-4-suite-connection-design.md` (cited "S§n"). Binding names: `docs/superpowers/specs/2026-10-07-crm-overhaul-interface-registry.md` (cited by handle: B12, C50, EV18, E24, H14). Programme contract: `docs/superpowers/specs/2026-10-07-crm-overhaul-programme-design.md` (cited "P§n": owner decisions M1 to M4 and D-1 to D-41, facts F1 to F11, release train P§10, register P§8).

## Plan status

This plan is at **release-outline level**. Each release below states its prerequisites, deploy order and verification, rollback and stop conditions, and a set of outline tasks: the files, the registry handles each task produces and consumes, the tests it must add and its commit boundary. It does not yet contain step-level tasks (failing test code, implementation code, exact commands, commits).

Each release is expanded to step-level TDD tasks with the writing-plans skill **at the start of that release**, on a branch cut from the `main` that holds its prerequisites, for three reasons:

- The first run's step-level parts for this sub-project were cut off by a usage limit: the R4.1 part stops after five of its tasks, the R4.4 part after its twelfth, and R4.5 to R4.7 were never reached.
- Later releases consume names that earlier releases create (R4.2 extends SP3's `SYSTEM_IN_APP_RULES`; R4.3, R4.4 and R4.5 extend the same customer consumer; R4.5 extends R4.3's finance and operations routes; R4.7 extends SP3's `owner_team` and `lead.scrub_lead_audit`). Code quoted now would be stale once R1 to R3 have merged, so each expansion first re-reads every symbol listed under "Consumes" in the merged code.
- Every release is owner-merged and manually deployed, so there is a natural pause before each one in which the expansion can be reviewed.

The unfinished drafts in `docs/superpowers/plans/_parts/crm-4-*.md` were used only as a source of verified file paths and task breakdowns; they are not part of the plan and are not executed. Their 21, 19, 30 and 12 cards for R4.1 to R4.4 are merged here into 14, 10, 11 and 8 outline tasks, and the decisions they flagged as DP-n are carried where the spec words something the code at `HEAD` cannot do. Alembic revision ids named here come from those drafts and were grep-verified unused at `HEAD` `3bc7f6ca`; a revision written "chosen at expansion" gets its id then. Each expansion re-verifies the id and sets `down_revision` to what `alembic heads` prints, at the `# RE-PARENT HERE` marker.

Conventions of this outline: `Task R4.n.m` numbers are stable handles the expansion keeps; "(exists after R<n>)" marks a file or symbol that an earlier release creates; **OWNER RUN** marks an act only the owner takes (a merge, a deploy, a box `.env` edit, a production read or write, a reconcile, an SPA publish, an owner-run tool), which an agent builds and tests and never runs (P§3 F11, S§13); `(DP-n)` marks a plan decision a reviewer can overturn; an error code is written in the spec's spelling and its test asserts the wire form, the RFC 7807 `type` suffix hyphenated as `CompanyDeletedProblem.problem_type = "company-deleted"` does, plus `errors[0].code` where the route uses `errors=[...]`.

## Global Constraints

Every task's requirements include this section. Values are copied from S§ header, S§4, S§17 and P§7.

- Base `main` @ `caa7f112`; the spec's `path:line` references were re-read at `HEAD` `3bc7f6ca`; Alembic heads at that commit: customer `e230c025337e`, deal `e94d7a2c5f18`, lead `91dd3ca663fd`, finance `faf3ff81d039`, notification `f1c8a2d5b7e4`, operations `d7a3c9e5b184`, support `d4e5f6a7b8c9`, project `c92e07b13fd5`, projects `c7b52e0a9f43`, storefront `ea0b8b84b84d`, marketing `96e4780b8df1`, approval `435fc681c9e5`, leave `e5b7c9d1a2f4`.
- Migrations are expand-only: `SET LOCAL lock_timeout = '5s'`, named constraints, one head per service, `down_revision` under a `# RE-PARENT HERE` comment, a downgrade that would destroy data raises `RuntimeError` unless `OPSGRIDS_ALLOW_DESTRUCTIVE_DOWNGRADE=1`, and a backfill runs in batches of 1000, each its own transaction, after the DDL has committed.
- Every table carries `organization_id`, is `ENABLE`d and `FORCE`d under the `tenant_isolation` policy on its schema's `current_org()`, and every selector and service query filters on `organization_id` as well (RLS is the net, never the permission to skip the filter); the tenant GUC is transaction-local; consumers and the outbox relay need `BYPASSRLS` or a per-message GUC.
- No cross-schema foreign key: a link is `crm_company_id` or `crm_contact_id` (`crm_lead_id`, `crm_deal_id` where named), plain `UUID NULL` with an index that leads with `organization_id` (`ix_<table>_org_crm_company`, `ix_<table>_org_crm_contact`); `customer_id` is never reused as a new column name; a link that cannot be proved stays `NULL` and the product keeps its display snapshot (SD-2, SD-3).
- Money is an integer in minor units beside an ISO currency, never a float or `Numeric(_, 2)`; figures are per currency and never summed across currencies; quantity times price rounds half-to-even once per line and every percentage of money (line discount, `discount_bps`, GST) rounds half-up (SD-14).
- Invoices, usage events, the credit ledger, `party_timeline`, `invoice_documents` and `deal.activities` are append-only and corrections are new rows; plan versions are immutable.
- Events are additive within `v1`; the payload change, its committed schema (`libs/contracts/events/<type>/v1.schema.json`, `additionalProperties: false`, `$id opsgrids://contracts/<type>/v1`) and a producer-side test through the real write path calling `platform_core.events.validate_event_schema` land in one commit; ids and enumerations only, never a name, address, e-mail, phone or free text; the envelope key is `organization_id`.
- A consumer deploys before the behaviour change of its producer (an event with no bound queue is dropped and an outbox row cannot be replayed); every handler binds the tenant from the envelope, cross-checks the payload organization and writes its marker in the same transaction as its effect; one handler per projected event with marker `uuid5(event_id, "party-projection")` (SD-4); every projection has a keyset export and an owner-run backfill.
- Background work is enqueued only after commit, through the outbox; a cross-service call is claim, call, record with no network inside a transaction (`tests/infra/test_io_outside_transaction.py`); the relay runs as `opsgrids_outbox`, which may read and update `outbox` and nothing else.
- Internal routes are `/internal/v1/organizations/{organization_id}/...`, `include_in_schema=False`, with a service token addressed to the callee, a per-route caller allow-list, an organization-claim check and 404 for a foreign id; customer's C50, C51, C52, C53 and C89 also re-check the `crm` entitlement (403 `crm_not_active`, 503 `entitlement_unavailable`).
- Authorization is server-side: every handler declares its permission with an explicit floor (`minimum=Scope.ORG` where the spec says so, so a customer-granted OWN rung cannot widen it), every list injects scope with `ctx.apply()`, and every endpoint has a negative-authz test (401, 403 missing permission, 403 below the scope floor, 402 not entitled, cross-tenant 404); a UI gate hides a control and protects nothing.
- PII is sealed and masked by default; an unmask needs its own permission and writes an audit row every time; audit rows for links hold ids only and no log line holds an address, number or name; consent stays in `notification` and CRM never decides it.
- An erase anonymises in place and emits `crm.book.contact.erased`; audit copies are rewritten by a `SECURITY DEFINER` function owned by `opsgrids_admin` that acts only on JSON objects and only on the session's own tenant.
- Production data is owner-run (P§3 F11): a tool is a parent process with no service import and one child per `--service`; `plan` is the read-only default; `apply` needs `--apply`, `--confirm-count N`, `--i-took-a-backup` and `--i-know-this-is-the-live-database`; one transaction per organization on the app role; counts-only output; idempotent.
- Permissions: catalogue, then `make openapi`, then deploy the enforcing service, then `make edge-reconcile PRODUCTS=<product>` (dry run first, then `APPLY=1`, off-peak, paced), and only then the UI; SPAs are published last from a checkout of the deployed `main` (`edge-web` builds the local checkout).
- Memory: no new container except ADR-0020's `insights`; each consumer fold is +1 MB (`api` 98 to `api_with_worker` 99) priced in its release; the owner raises `EDGE_BUDGET_ACCEPTED_MB` by hand (3947 support, 3948 marketing, 3949 storefront, insights +99, the PDF library measured and priced as `api_with_worker_render`); the preflight is the stop condition.
- Frontend: shared components live in `@opsgrids/ui` and `@opsgrids/client` and are never forked into `product-crm`; `pnpm tokens:baseline` without `--allow-increase` writes nothing; every changed or new screen has loading, empty, error and forbidden states at 375 px with no horizontal scroll at 360 px; a story per new `@opsgrids/ui` export; a fixture and `MockRoute` per new `GET` a harness app calls; no new axe violation.
- Verification per release: the per-service `pytest` and `mypy` loop (`import app` is ambiguous across services), `make check`, `make gate` locally (Actions billing is blocked), `make openapi` and `make openapi-check`, `make contracts-check`, `make migration-roundtrip`, and `make ui-visual` for any UI release.
- Deploys are manual, name a ref and stop on the first failure; the owner squash-merges each release; no MinIO rotation, session cap or production configuration edit happens without the owner's approval.
- Commit messages must not mention Claude, Claude Code, or any AI assistant, and carry no generated-by footer and no co-author trailer; branches are short-lived `feat/crm-r4-<n>-<slug>`, one PR per release (per stage for R4.5 and R4.6), squash merge by the owner; never commit `.env` or secrets.

## Review Focus

The five input classes or failure modes the spec implies that no test in its tables exercises, most likely first. Each is pinned by a test added to the named task.

1. **PDF text outside Latin-1.** A quote or invoice PDF whose buyer, address or item names hold the rupee sign (U+20B9) or Devanagari or Tamil text, which an Indian tenant's ordinary data does: a person expects legible text from an embedded Unicode font, never a crash, a blank box or a `?`. Pinned by Task R4.5.8, `test_pdf_text_round_trips_rupee_devanagari_and_tamil` over a fixture quote and a fixture invoice.
2. **A quote accepted on its last day.** A buyer accepts a `sent` quote late on the evening of `valid_until` in the organization's own calendar, and again an hour after midnight: a person expects acceptance through the whole of that date in `deal.pipeline_settings.timezone` (B65) and a 409 `quote_expired` after it, with the scheduled expiry, the `:accept` check and the status chip agreeing on one instant (S§10.4 arms the job at `valid_until + 1 day, 00:00 UTC` and refuses a past-date `:accept` without naming a zone, so the two disagree for every organization whose calendar is not UTC). Pinned by Task R4.5.4 (DP-4.5-1), `test_accept_on_the_last_day_at_2330_and_0030_local`.
3. **An erase that races work already in flight.** A campaign run or automation delay holds a pending send to the contact, or a product proved the contact through C89 a moment before the erase and records its link just after the handler ran: a person expects no message to reach the tombstone and none to retry in a loop (pending sends become `suppressed`), and a late link to be cleared by the next H14 pass and counted `erased_linked` by the orphan sweep. Pinned by Task R4.2.5 (`test_erase_suppresses_pending_sends_to_the_contact`), Task R4.1.12 (`test_a_link_written_after_the_handler_ran_is_cleared_by_the_next_pass`) and Task R4.7.7 (`test_a_late_link_to_an_erased_contact_is_counted_erased_linked`).
4. **An amount in a currency whose minor unit is not 1/100.** JPY has none and KWD has three; the quote composer, the finance credit limit and Marketing's manual adjustment convert typed amounts to minor units: a person expects the currency's own exponent (`platform_core.money.exponent` on the server, the SPA's `parseMinor`), never a multiplication by 100 (`formatMoney` is tested for a zero-decimal currency in S§8.7; the input direction is not). Pinned by Task R4.5.7 (`test_composer_converts_with_the_currency_exponent`), Task R4.3.11 (`test_credit_limit_uses_the_currency_exponent`) and Task R4.6.3 (`test_manual_adjustment_uses_the_currency_exponent`).
5. **A company with a very long commercial history.** A wholesaler with ten years and tens of thousands of invoices and payments: a person expects one event to cost one aggregate under the per-company lock, the 360 to read bounded rows (the rollup and a limited latest-document read) and the nightly sweep to stay bounded. Pinned by Task R4.3.8, `test_projection_of_one_event_is_constant_in_a_company_with_20000_documents` (a statement counter, not a wall-clock threshold).

### Rollback and stop conditions

The first lever is not to roll back: nothing consumes R4.1 and the previous images ignore the new column, function, routes and fields. SPAs roll back with `make edge-web-rollback … APP=<app>`. The schema stays; a downgrade is a separate owner-approved act that refuses while an erased contact exists. Consumers: none bound, so nothing is discarded. **Do not roll the customer image back once any contact has been erased** (the previous image would accept an edit on an erased row; fix forward: S§6.10, S§17 item 12a). Stop: the customer migration fails or holds the lock over 5 s; a synthetic erase leaves the address in any audit row of that contact; an erase stages no EV18 row; a producer test fails its schema; a C58 write appears without its ledger row.

### Rollback and stop conditions

Levers that lose nothing are configuration: an organization's administrator switches `order_invoice_chain_enabled` off (one `PUT`); the owner sets `ORDER_INVOICE_CHAIN_MODE=log_only` (or `off`) and `CREDIT_CHECK_MODE=warn`; an administrator sets `lifecycle_promotion` back to `off`. Code rolls back to the previous images and the schema stays. Not reversible: invoices the chain issued (a credit note corrects them), payments and allocations, e-invoice filings, lifecycle promotions (`lifecycle_promoted_at` stays), a `crm_company_id` written by H2 (its audit counts let the owner nullify exactly those rows). Stop: a parity test fails after H4; a paid order has no payment row after the sweep ran; two payments for one `charge_id`; an order invoice with a NULL place of supply, for an organization that did not opt in, or at a rate it did not choose; `finance.orders.invoice.request_rejected` events rising after the flip; `customer.events.dlq`, `finance.events.dlq` or `operations.events.dlq` depth rising; a rollback of finance, customer or operations while its queue carries live traffic without its catch-up ready, and never a finance rollback during live online captures unless payment already serves C105.

| Consumer (queue) | Lost on a code rollback | Catch-up |
|---|---|---|
| customer projection handlers (`customer.events`) | document, payment and rollup facts of events published meanwhile | H4 rebuilds them from the C63 exports |
| customer timeline lines and lifecycle promotion | one line per lost event; a promotion a lost event would have made | forward-only: the timeline is "recent activity" and the claim is idempotent, H4 never promotes |
| finance capture handler (`finance.events`) | the capture of a paid order | `reconcile_online_captures` pages C105 (the last 30 days) |
| finance and operations erase handlers | erasures while the old image runs | H14 `--service finance`, `--service operations` |

### Rollback and stop conditions

Without a rollback: set `create_project_on_won` to false (one `PUT`) and unbind nothing. Code rolls back to the previous images and the schema stays; the lever that loses nothing is `RUN_CONSUMERS_IN_API=false` with `split-workers` (S§4.7).
