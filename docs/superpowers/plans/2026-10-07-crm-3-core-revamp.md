# Sub-project 3: CRM core revamp (features and UI) Implementation Plan (release outlines)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (- [ ]) syntax for tracking.

**Goal:** Turn the CRM's three services (customer, deal, lead) and one SPA (`product-crm`) from a thin CRUD front over a six-stage board into the daily-use tool a small sales team works from, in eight independently releasable steps (R3.1 to R3.8), without breaking tenant isolation, append-only records, sealed PII with audited reveal, server-side authorization, money in integer minor units, or the one-box memory budget.

**Architecture:** Backend changes are expand-only and staged: tolerant readers deploy before the writes that need them (R3.1a before R3.1b, R3.7a before R3.7b, TEAM wiring inert before the widening). Three shared platform modules carry the cross-service behaviour (`platform_core.gst`, `platform_core.listing`, the problem documents in `platform_core.errors`), plus the scheduler's first cancel in `platform_core.events`. The UI promotes shared components to `@opsgrids/ui` and `@opsgrids/client` first (R3.3), then rebuilds each CRM screen on them behind a route registry (R3.4 to R3.8), and every removal follows the rule replace, then delete.

**Tech Stack:** Python 3.12 (FastAPI 0.115+, Pydantic 2.9+, SQLAlchemy 2 async, Alembic 1.14+), PostgreSQL 16 with row-level security and a schema per service, RabbitMQ events through the outbox, Redis for capture budgets; TypeScript 5.7, React 19, Vite 7, Vitest 3, `@opsgrids/ui`, `@opsgrids/client`, `openapi-typescript` (R3.2), the Playwright and axe visual harness (`make ui-visual`); Docker Compose edge box.

**Spec:** `docs/superpowers/specs/2026-10-07-crm-3-core-revamp-design.md` (cited `S§n`; its design decisions are `DD-n`, risks `K-n`, owner steps `O-n`). Binding names: `docs/superpowers/specs/2026-10-07-crm-overhaul-interface-registry.md` (`REG`, cited by handle: A15, B6, C22, EV19, G1, H8 and so on). Programme contract: `docs/superpowers/specs/2026-10-07-crm-overhaul-programme-design.md` (`P§n`; owner decisions `D-n` are the rows of P§8; facts `F1` to `F11` are P§3).

## Plan status

This plan is at **release-outline level**. Each release below states its prerequisites, deploy order, rollback and stop conditions, then outline tasks that name files, produced and consumed interfaces, tests and one commit boundary. It contains no test code, no implementation code and no step-by-step commands. **At the start of each release, that release alone is expanded to step-level tasks (failing test code, implementation code, exact commands, commits) with the writing-plans skill**, reading the tree as it is then. Until a release is expanded, each task carries one checkbox, ticked when its tests pass and its commit is made.

Why: later releases consume interfaces that earlier releases produce, and those releases (SP1, SP2 and the earlier SP3 releases) change `services/*/app/*.py`, the three `test_authz_matrix.py` files, `frontend/product-crm/src/api/client.ts`, the visual fixtures and `libs/platform-core` before a later release touches them, so step-level code written now would be stale when it runs. Most releases also wait on owner decisions that are still open (P§8: no plan task that depends on an open row starts). A first run's step-level drafts for this sub-project (`docs/superpowers/plans/_parts/crm-3-*.md`) were cut off by a usage limit: they are complete for part of R3.1 and R3.2, task cards for R3.4 to R3.7, four cards for R3.8 and nothing for R3.3. They were used only as a source of verified file paths and task breakdowns and are superseded by this outline.

Conventions: a path with no marker exists at `3bc7f6ca`; **(new)** is created by this plan; **(R1.1)**, **(R1.2a)**, **(R2.2)** and so on name the earlier release that creates it; `<rev>` is an Alembic revision id fixed when the release starts; within one Files bullet a path that does not start at a top-level directory (`app/…`, `tests/…`, `routes/…`, or a bare file name) is relative to the service or application directory of the nearest full path before it; a line cite is where the text was at `3bc7f6ca`, and the symbol named beside it, not the number, locates an edit once earlier releases have landed. **OWNER RUN** marks an act only the owner takes (S§13); an agent builds and tests locally and never merges, deploys, reads or writes production, or edits the box `.env`. Releases run in the order of P§10; SP3 and SP4 releases interleave by readiness. Before R3.1 starts the owner answers O1: the decisions of S§2.1, including those reached through SP2 and SP4, and acknowledges the one-way points K1 to K3.

## Global Constraints

Every task's requirements include these lines.

- Commit messages must not mention Claude, Claude Code, or any AI assistant; no generated-by footers, no co-author trailers, no attribution lines in pull request bodies; messages read `Area: what changed`; never commit `.env` or secrets (CLAUDE.md, P§7).
- Short-lived `feat/crm-r3-<n>-<slug>` branches, one per release (two for R3.1, R3.7 and R3.8), one commit per task, one pull request per release, squash-merged by the owner; an agent never merges its own pull request (P§3 F11).
- Review, merge, manual deploy, verify, stop on any failure; no agent runs a deploy, a `make edge-*` target, a production tool, a production read or write, `e2e/edge_product_crud.py`, or edits the box `.env` (P§3 F11, S§13).
- Every table carries `organization_id` and every query filters on it as well as RLS; every index leads with it; the tenant GUC is transaction-local (`set_config('app.organization_id', …, true)`); background work is enqueued only after commit through the outbox.
- A new table has the `TenantBase` columns, `ENABLE` and `FORCE ROW LEVEL SECURITY`, the policy `tenant_isolation` `FOR ALL TO <app role>` with `USING` and `WITH CHECK` on `<schema>.current_org()`, and a `TENANT_TABLES` entry in the service's `tests/conftest.py`; no `GRANT` is written (`apply_schema_grants` runs after every migration); no cross-schema foreign key, a link to another schema is a plain indexed UUID.
- Every migration starts `SET LOCAL lock_timeout = '5s'`, is expand-only, is one revision per service per release, states its downgrade, and a downgrade that would lose rows raises `RuntimeError` unless `OPSGRIDS_ALLOW_DESTRUCTIVE_DOWNGRADE=1`; each `down_revision` is the service's head at merge with the marker `# RE-PARENT HERE` (heads at `3bc7f6ca`: customer `e230c025337e`, deal `e94d7a2c5f18`, lead `91dd3ca663fd`, scheduler `bff4691114ce`); data steps are set-based, idempotent, need no PII key and log counts only.
- Money is integer minor units with an ISO currency, never a float and never summed across currencies; a deal's weighted value is `(value_minor * probability + 50) // 100` and a win rate is `(200 * won + decided) // (2 * decided)`, both half up (DD-9); the legacy summary field answers 0 when nothing is decided and the Reports answer null.
- Events carry ids and enumerations only, never an email, phone, name or free text; each event's committed schema (`libs/contracts/events/<type>/v1.schema.json`, `$id opsgrids://contracts/<type>/v1`, `additionalProperties: false`) lands in the same commit as its producer, with a producer-side test through the real write path and `validate_event_schema`; a consumer deploys before its producer's behaviour changes.
- Every consumer runs `already_processed` and `mark_processed` in the same transaction as its effect, binds the tenant per message with `session_scope(organization_id=…)`, and refuses an envelope whose `organization_id` differs from the payload's; no handler holds a transaction across a network call (`tests/infra/test_io_outside_transaction.py`).
- A sealed value (phone, lead email) is never returned, logged, put in an event, an audit `after`, a URL or a query string; identifier lookups are `POST` bodies; reveal keeps `require(code, amr={"otp", "stepup"})`, the shared Redis budget and an audit row every time.
- Authorization is server-side and a UI gate hides a control only: each route declares `require(code, minimum=...)` and `Entitled`, lists apply `ctx.apply(...)`, details `ctx.assert_can_touch(...)`, a foreign or missing id is the same 404, static paths are declared before `/{id}`, and no SP3 code reads `ctx.subject_ref` (it uses `ctx.own_ref`).
- Every public route gets a row in its service's `test_authz_matrix.py` (R3.1.3) and named negative tests: no token 401, lacking the permission 403, below the scope floor 403, no `crm` entitlement 402, another organization's id 404; every internal route gets three (no token 401, wrong caller 403, wrong organization claim 403).
- SP3 creates no permission code (E18 to E22 are catalogued by SP2); `python tools/export_permissions.py --check` passes unchanged; a code reaches live tenants by `make edge-reconcile PRODUCTS=crm` (dry run first, then `APPLY=1`, off-peak, paced) before the SPA that shows the control.
- Audit rows for contacts carry `changed_fields` names only; tax-id, address and legal-name writes audit ids and field names only (DD-48); history projections are allow-lists and contacts and leads never return a value.
- Tests and typecheck loop per service because `import app` is ambiguous across services (`make typecheck-services`, `make test-services`); `make gate` runs locally because GitHub Actions billing is blocked, and `make ui-visual` is run by name for a UI release (S§4.5 S1 to S8).
- Shared UI lives in `@opsgrids/ui` and `@opsgrids/client` and is never forked into `product-crm`; `@opsgrids/ui` may not import `@opsgrids/client`; new code has zero token offenders and `frontend/opsgrids-config/token-baseline.json` only shrinks (97 offenders in 14 files when R3.4 starts, 0 after R3.7); every screen has loading, empty, error and forbidden states; every new `GET` has a `MockRoute` and a fixture; new pages start with no a11y baseline entry.
- Lists: `size` is 25, 50 or 100; `ids` at most 100; organization timezone default `Asia/Kolkata`; `sort` ends in an `id` tie-break; a note-only visitor message goes to `capture_messages` (at most five entries of 2,000 characters), never `notes`; tags at most 20 per record matching `^[a-z0-9][a-z0-9 _-]{0,39}$`; saved views at most 50 per member per entity.
- Replace, then delete: a removal with a live user ships after its replacement, in the order replacements, consumers moved, deletions, with a proof (`ls` or `grep`) in `removed.test.ts`.
- Memory is stated as a change against the totals `python3 infrastructure/edge/lib/memory_budget_totals.py infrastructure/edge/memory-budget.json --profiles <list>` prints at the parent commit, for `""`, `crm`, the ten sellable profiles and the same list with `admin` (at `3bc7f6ca`: 1772, 2067, 3747, 3944); every consumer fold is +1 MB (REG F8); only the owner raises `EDGE_BUDGET_ACCEPTED_MB`, to the total `make edge-preflight` prints for the deploy being made.

## Review Focus

Inputs the spec implies that no test of S§5.7 to S§12.7 exercises, most likely first; each is pinned by the test named at the end of its line.

1. A WhatsApp-first user imports a sheet of contacts that have a phone and no email, then edits and exports them: rows import (or fail with a per-row message), duplicates match on the phone, and nothing renders `mailto:` or "undefined"; pinned by `contacts_import_accepts_a_row_with_a_phone_and_no_email` in Task R3.4.8 and the API round trip in Task R3.1.15.
2. Money typed or pasted in another notation (`1.200,50`, a currency symbol, "12 lakh", too many decimals) must be refused with a message that states the accepted form, never read as a different amount; pinned by `format.money.test.ts` in Task R3.3.1 and shown by the deal form of Task R3.4.9.
3. Names in Devanagari, Tamil or with accents: `q` search is case-insensitive over them, sort is stable, and a tag such as `Delhi/NCR` or `दिल्ली` is a field error that names the allowed characters, not a 500 or a silently altered value; pinned by Task R3.2.1 (`listing` helper tests) and Task R3.8.1 (`normalise_tags`).
4. A closed deal whose close reason was archived afterwards still shows the reason's label (page and Reports), not a blank or a raw key; pinned by `closed_deal_shows_the_label_of_a_reason_archived_after_the_close` in Task R3.5.9 and the Reports tests of Task R3.8.12.
5. Erasing a lead that other records still point at (a newer lead's duplicate pointer, an open follow-up with a free-text title, a duplicate banner on another lead page): pointers read as null and every lookup reads "Not available", never "Unassigned" or a raw id; pinned by `test_a_duplicate_pointer_at_an_erased_lead_reads_as_null` in Task R3.7.3 and the lead-page tests of Task R3.7.9.
