# The workflow — every card, every time

You will do this same sequence for every card you are ever given. It does not change.

There are two branches you must know about:

- **`development`** — where everyone's finished work is collected. You branch **from** it and
  you open pull requests **into** it. You never commit to it directly.
- **`main`** — the release branch. You will never touch it. Ever.

---

## The nine commands

```bash
# 1. Start from the latest development. Do this every time, even if you did it yesterday.
git checkout development
git pull origin development

# 2. Make your branch. The card gives you the exact name — copy it, do not invent one.
git checkout -b feat/a1-lead-model

# 3. Do the work the card describes. Only the files the card lists.

# 4. Run the card's DONE WHEN commands. Do not go to step 5 until they all pass.

# 5. Look at what you are about to commit. Read this output.
git status

# 6. Stage everything.
git add -A

# 7. Commit, with a plain sentence describing what you did.
git commit -m "Add the lead domain table"

# 8. Push your branch.
git push -u origin feat/a1-lead-model

# 9. Open the pull request, targeting development.
gh pr create --base development --fill
```

Then fill in the pull request template — especially the **DONE WHEN output** box — and request
review from `@developer-sanyam`.

---

## What happens next

1. **You wait.** Do not merge. You cannot merge, and you must not ask to.
2. **Review comes back.** If changes are requested, fix them **on the same branch**:
   ```bash
   # you are still on feat/a1-lead-model
   git add -A
   git commit -m "Use the true minus sign in the delta label"
   git push
   ```
   The pull request updates itself. **Never open a second pull request for the same card.**
3. **It gets merged** by the reviewer, into `development`.
4. **You start the next card from scratch:**
   ```bash
   git checkout development
   git pull origin development
   git checkout -b feat/a2-lead-rls
   ```

You may delete your old branch after it is merged; you never need it again.

---

## Commit messages

A plain, complete sentence in the imperative, describing what the change does.

Good:

```
Add the lead domain table
Give listAttendance a live branch
Test the delta formatter's true-minus sign
```

Bad:

```
fix                      (fix what?)
WIP                      (then do not commit it)
Update models.py         (that is the filename, not the change)
Added lead table :)      (past tense, and no emoji)
```

**Never mention Claude, Claude Code, ChatGPT, Copilot or any AI assistant in a commit
message.** No "generated by" footers, no `Co-Authored-By` trailers. Write as the engineer of
record. This is a rule in `CLAUDE.md`, not a preference.

## Things that will go wrong, and what they mean

**"Your branch is behind 'origin/development'"**
You started from a stale copy. Fix:
```bash
git checkout development && git pull origin development
git checkout feat/your-branch
git rebase development
```
If the rebase reports a conflict, **stop and comment on the card.** Do not resolve it by
guessing which side is right.

**"Updates were rejected because the remote contains work that you do not have"**
Someone pushed to your branch, or you are on the wrong branch. Run `git status` and
`git branch --show-current`, then comment. **Never use `--force`.**

**You committed on `development` by accident**
Stop. Do not push. Comment on the card with the output of `git log --oneline -3` and wait.

**Your pull request says "This branch has conflicts"**
Comment on the card. Merge conflicts are a reviewer's job on this team, not yours.

---

## The one rule that matters more than all of the above

> **If the card does not say it, do not decide it. Comment and wait.**

Waiting an hour for an answer costs an hour. Guessing costs a day of your time, an hour of
review, and sometimes a database migration that has to be unpicked. Nobody on this team will
ever be annoyed that you asked.
