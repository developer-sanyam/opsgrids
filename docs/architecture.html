OpsGrids Platform Map

One organization, one account, one user directory — and every product activated on top of it. Thirty-four Python microservices behind two gateways, one PostgreSQL cluster with a schema per service, and a domain-event backbone. Click any service for detail, or trace a journey end to end.

The whole system, one screen

Clients reach one of two gateways. The gateway verifies the token once, resolves the organization, injects tenant context, and refuses anything the organization has not activated. Everything below it owns its own schema and talks over REST and events.

Why two gateways

app-gateway is a backend-for-frontend: it shapes payloads per screen and is allowed to be chatty downstream. admin-gateway fronts internal, operator and partner APIs. Splitting them keeps consumer latency work and operator breadth from trading off against each other — and keeps the super-admin surface from ever being one routing mistake away from public.

The tenancy rule

Organization-scoped rows in a shared schema: organization_id on every table, every query filtered — and PostgreSQL row-level security underneath. The filter is the design; RLS is the net, because "isolation is a query concern" otherwise depends on every developer remembering, forever.

The trap that follows: outbox relays and fan-out consumers legitimately span every organization. They run as a BYPASSRLS role. Run one as the app role without setting the tenant GUC per message and event processing stops silently — nothing errors, the outbox just fills.

Event topics

Routing key is <product>.<aggregate>.<verb> on one durable topic exchange, opsgrids.events. Publishing goes through a transactional outbox, so an event and the state change it describes commit together or not at all.

Delivery guarantees

At-least-once. Every consumer checks a processed_events ledger before acting and marks the id in the same transaction as its side effects — a redelivered event that increments a counter twice produces a number nobody can explain later.

Every projection also has a scheduled reconciler. The outbox guarantees at-least-once, not eventually-correct-after-a-dead-letter, and a DLQ nobody watches is data loss with extra steps.

Products

Each is independently activatable. Activating one never means a new account, a second user directory, or re-uploading people — it flips an entitlement on an organization that already exists.

Adding product N

The checklist this architecture exists to make true. If any step needs a change to the core, the core is wrong.

  1. Reserve a product key; insert a row in product-service.
  2. Claim URL prefixes in the gateway route registry — config-driven, never a code edit.
  3. Publish a permission manifest; account-service registers it.
  4. Ship role templates the platform instantiates per organization.
  5. Declare plan features and usage metrics to catalog-service.
  6. Declare the event catalogue as JSON Schema in libs/contracts.
  7. Declare projections and register their reconcilers.
  8. Register notification templates and file scopes.
  9. Emit audit through the shared mixin — never a bespoke log table.
  10. Publish OpenAPI into the docs hub.
  11. Implement lifecycle consumers: access granted and revoked, membership revoked, org suspended.
  12. State the data contract on revocation and deletion.
  13. Meet the test bar: negative-authz per endpoint, idempotency per consumer, drift per projection, contract per event.
  14. Add it to the marketplace.

Cross-cutting

The concerns every service shares, and how the whole thing ships.

Identity and tokens

auth-service holds the only private signing key; everything else verifies through JWKS. EdDSA with a kid, two keys live at all times, rotation is publish-then-switch. A product can verify a token and cannot forge one.

Tokens are per audience and carry no permission list. Five products at roughly forty permissions each is 5–6 KB of header once encoded — past common proxy limits, where it is truncated and surfaces as a silent 500. The gateway resolves permissions per request against a cache keyed by the pv claim, so a revoked grant takes effect on the next request rather than when the token expires.

Headers injected downstream: X-Org-Id, X-User-Id, X-Membership-Id, X-Perms, X-Entitlements, X-Correlation-ID, X-Internal-Token. A service trusts them only when the internal token matches.

Permissions

Four levels: product.module.resource.action:SCOPE. Stored normalised with actions as data rows, so a new verb needs no schema change. Scopes are OWN < TEAM < LOCATION < ORG, and how each rung becomes a query filter is registered per product — CRM's natural narrowing is territory, HR's is the reporting line, and forcing one reading on both is the decision most likely to be regretted.

Observability

Structured logs with a correlation id minted at the edge and threaded through every log line and every event envelope, so one request crossing five services is one searchable thing. Audit is a shared mixin written inside the transaction it describes — including reads of sensitive data, because unmasking PII is an auditable event in its own right.

Deployment

Kubernetes with Helm and kustomize, per-customer overlays for enterprise, horizontal autoscaling. Each service ships three entrypoints — bin/api, bin/worker, bin/cron — so a slow consumer can never block an API request. CI lints, typechecks and tests one service per process, because each exposes a top-level app and two cannot share an interpreter.
